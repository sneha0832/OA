## 1. Which endpoints did you add, and why does this system need them?

> `DELETE /api/v1/employee/{uuid}` — This allows a consumer to remove an employee using their UUID. I chose DELETE because it complements the required create and read operations and provides a useful additional employee-management operation.
>`GET /api/v1/employee/search?name={name}` — allows a consumer to search employees by first name, last name, or full name. The search is case-insensitive and supports partial matches to make employee lookup more flexible.
>I chose these endpoints because they add useful employee-management functionality while keeping the API focused and within the scope of the challenge.

## 2. Did you add any dependency? What does it buy, and what does it cost?

> I did not add any dependencies. The existing Spring Boot and testing dependencies provided everything needed to implement and test the API. Avoiding additional dependencies keeps the project simpler and avoids adding unnecessary maintenance or compatibility concerns.


## 3. How did you handle errors and logging, and why those mechanisms?

> For errors, I used `ResponseStatusException` to return appropriate HTTP status codes. Invalid employee data returns `400 Bad Request`, missing employees return `404 Not Found`, and malformed UUIDs are rejected by Spring's request parameter conversion with `400 Bad Request`. I chose this approach because it is simple and sufficient for the scope of this API without introducing additional exception-handling classes.
>I added operational logging for employee creation, deletion, and failed UUID lookups. The logs use employee UUIDs to identify operations without logging unnecessary employee information such as email, salary, or request bodies.

## 4. Where the brief left a decision to you, what did you decide?

> I created a service layer so that business logic is separated from the HTTP/controller layer. Employees are stored in an in-memory `ConcurrentHashMap` keyed by UUID because the challenge does not require a persistence layer.
>I also created a `CreateEmployeeRequest` DTO rather than accepting an `Employee` directly. The request contains only values the client should provide. The service generates the employee UUID and derives `fullName` from `firstName` and `lastName`.
>I treated `firstName`, `lastName`, `salary`, `age`, `jobTitle`, `email`, and `contractHireDate` as required create fields, while `contractTerminationDate` remains optional as specified in the brief. ## 5. What did you deliberately choose *not* to do?

> I deliberately chose not to expose uuid or fullName as fields that the client controls when creating an employee. The UUID is generated by the service, and fullName is derived from the employee's first and last name, which avoids inconsistent or client-supplied values.
> I also chose not to add update functionality (PUT or PATCH). Instead, I focused the additional endpoints on deletion and name-based search and made sure those behaviors were tested. I would add update functionality if modifying existing employee records became a requirement.
